### The exe is modified (confirms risk R1)
- Every section in `MaxPayne.exe` has flags `0xC0000040` (initialized data, read/write, **no execute**). A normal MSVC link marks `.text` as code, so something rewrote the section table.
- Extra sections `stxt774`, `stxt371`, `.MGD32` (together ~48 KB) look like copy-protection leftovers.
- `.text` entropy (6.57) looks like ordinary code, not encrypted, so a survey is possible, but the exe is **not a trustworthy basis for the lift**. Wait for the clean store build.

- **No SSE, SSE2, 3DNow! or AVX** found. The game is x87 + integer code; MMX is limited to a few `emms` sites.

### MFC42
- `MFC42.DLL` here exports **only ordinals** (6 named of 6,388). Names must come from an external ordinal table (Wine `mfc42.spec` was not reachable at the path I tried; try the MFC 4.2 `.def` files or build a table from Ghidra).
- Engine DLLs use only #823 and #825 (very likely `operator new` / `operator delete` wrappers, verify). Everything else is the **exe's app shell**, which is what makes bypassing `CWinApp` (decision D4) realistic.
- `MFC42.DLL` itself imports 120 KERNEL32, 195 USER32, 111 GDI32 functions, so lifting it would drag in a large user32/gdi32 shim. Prefer to bypass.

## 4. Timing (for the 60 fps goal)
- `R_Timer` (rlmfc) exposes `sample`, `getDelta`, `getAge`, `pause`, `resume`, `reset` with **float** time values, which suggests variable timestep rather than a fixed tick. **Not yet confirmed**; the main loop needs to be read in the clean exe.
- Time sources: `QueryPerformanceCounter/Frequency`, `timeGetTime`, `rdtsc` (speed test). `R_Profile` tracks frame start/end and frame count; `P_Statistics` has frame/swap/buffer-lock timers in e2mfc.

## 5. Renderer seam (for D2)
- The driver DLL imports 218 functions from `e2mfc.dll`; those are the engine's `P_*` base classes it extends. The driver's own surface is `P_D3D : P_Driver` with `DRV_*` virtuals.
- Direct3D 8 itself is loaded dynamically (`D3D8.DLL` string in the exe plus `LoadLibraryA`/`GetProcAddress`), not statically imported, so instrumenting means hooking the loaded interface, not an import table.

### Exe startup (the exe is **not** an unpacker stub)
- Entry `0x76fb04` is the ordinary MSVC CRT startup: `__set_app_type`, `__getmainargs`, `_initterm` ×2, `GetStartupInfoA`, `GetModuleHandleA`, then `exit(WinMain(...))`.
- `WinMain` (`0x783860`) is a one-line wrapper that calls `MFC42!AfxWinMain`, so the app is a normal shared-MFC `CWinApp` program. Bypassing it (decision D4) means supplying our own entry that runs what `CMaxPayneApp::InitInstance` does.
- Ghidra names only six MFC ordinals (`AfxWinMain`, `AfxGetThreadState`, `AfxGetModuleState`, `AfxMessageBox`, `AfxFindResourceHandle`, `AfxRegisterWndClass`). The other ~139 stay unnamed.

### Things the RTTI names tell us (exe has 2,209 classes)
- `CMaxPayneApp` is the app class; `CMaxPayneStartupDialog`, `MaxPayneAdvancedDialog` and two parental-lock dialogs are the MFC dialogs to replace with a native launcher.
- `MaxPayneAppException_InvalidFPUPrecision` and `..._InvalidFPURounding`: the game **checks the x87 control word** at runtime and refuses to run with the wrong precision or rounding. An x87 model must expose a control word, and the correct mode is probably 53- or 64-bit precision with round-to-nearest (confirm from the check in the exe).
- Game-speed messages (`ChangeGameSpeed`, `ChangeGlobalGameSpeed`, `ChangeControlledGameSpeed`, `EnableBulletTime`) suggest bullet time works by scaling a time multiplier, which fits a variable-timestep design.
- `MaxPayne_GameModeMessage_EnableWideScreen` and `ChangeFOV` exist: the engine already has a (probably letterbox-cinematic) widescreen mode and an FOV control. Look at them in M7 before inventing new hooks.
- No class names for Havok or Karma were found, so the physics and ragdoll code appears to be in-house.

## 7. Required x87 mode and the per-frame function (M1 finding)

**The game requires x87 precision control = 53 bits (double) and rounding = round-to-nearest, and checks it every frame.**

- `FUN_0040c020` (exe, `0x40c020`, a `CMaxPayneApp` method taking `this` in ECX) runs once per main-loop iteration. It creates an `M_FPUControl` and throws `MaxPayneAppException_InvalidFPUPrecision` unless `getPrecision() == 0x200`, and `..._InvalidFPURounding` unless `getRounding() == 0`. Strings in the exe say the same: "FPU precision is assumed to be 53 bits", "FPU rounding is assumed to be 'near'".
- `M_FPUControl::getPrecision` returns `FPUControlWord & 0x300`; `getRounding` returns `FPUControlWord & 0xC00` (rlmfc, `0xab40` / `0xab20`). So the required control word has PC = `10b` and RC = `00b`, which is the usual MSVC value `0x027F` with exceptions masked.
- Decompiled copy: `census/decomp/exe_main_loop_0x40c020.c` (gitignored).

**What this means for the lifter (risk R2 is much smaller than feared):**
- With 53-bit precision the x87 rounds each result to a double mantissa, so modelling x87 registers as C `double` is **bit-exact for + - * / sqrt** in normal ranges. What can still differ: the extended exponent range (overflow/underflow/denormal edge cases), `fsin`/`fcos`/`fpatan`/`f2xm1`/`fyl2x` results (the hardware's last-bit behavior vs libm), and 32-bit stores/loads, which round or widen exactly as in C.
- The ~264 `fldcw` sites need a look: expect the compiler's float-to-int pattern (`fnstcw`, set truncate bits, `fldcw`, `fistp`, restore). Model these as a scoped truncating conversion, not as a real control-word change. Any `fldcw` that sets 64-bit precision or non-nearest rounding for longer than one conversion must be listed individually.
- The game itself fails fast when the mode is wrong, which also means **the host must start the guest with CW = 0x027F**, and anything that Direct3D 8 does to the control word (device creation without `D3DCREATE_FPU_PRESERVE` normally drops it to 24-bit) is not our problem once D3D8 is our own code.

## 8. What the per-frame function tells us about timing (M7 input)

`FUN_0040c020` also does the frame-time handling, so the 60 fps question is mostly answered:

1. `dt = R_Timer::sample(timer)`, then **clamped to at most 0.1 s** (constant `0x3dcccccd` at `0x7cb8b4`; the minimum is not clamped).
2. `dt` goes into a **ring buffer of recent frame times** (buffer at `this+0xe5`, write index `+0xe9`, count `+0xed`, capacity `+0xf1`). The function takes the **average over the buffer**, adds it to a running total time (`this+0xf5`), and calls `FUN_00582df0(avgDt, totalTime, 1.0f)`, which presumably publishes the game clock and a time scale.
3. It then runs the update (`FUN_0040e530`, `FUN_0040cd70`, `FUN_00601250(ctx, R_Timer::getDelta())`), updates the sound listener, and pumps Windows messages (`PeekMessageA`, `TranslateMessage`, `DispatchMessageA`, `WM_QUIT`).

So the simulation is **variable-timestep with smoothed dt**, not a fixed tick. That favors a simple 60 fps path: present at the display rate and let `R_Timer` report ~16.7 ms. Still to check in M7: whether physics, animation and AI sub-step or hard-code 30/60 Hz inside `FUN_00601250`, how bullet time (game-speed scale) feeds in, and whether anything else caps the frame rate (vsync mode in the driver's `P_DisplayMode`, or a `Sleep`).

### 8.1 Follow-up reads (update chain and frame caps)
- `FUN_00601250(ctx, dt)` (`0x601250`) is the **game-mode manager update**: it reads a global/scaled time factor (`FUN_005e53d0`, `FUN_005830d0`), updates the active mode and every overlaid mode through virtual calls, and passes the **scaled `dt`** down. It has no inner sub-step loop of its own, so any sub-stepping (physics, AI, animation) happens deeper in the mode `update` virtuals. These are the next thing to read for the 60 fps work.
- `FUN_00582df0` is a small constructor-style call that stores the (avg dt, total time, 1.0f) triple into a clock object (vtable `0x7d142c`).
- **No frame limiter found in the exe.** The only `Sleep` call (`0x409f02`) is inside `FUN_00409ac0`, the **intro-movie player**: it does `CoInitialize`, `CoCreateInstance` (DirectShow), a message loop, and builds an `M_FPUControl` (DirectShow changes the FPU mode, so the game re-checks it). It is not a frame cap, and it tells us the movie player must be replaced as a whole (M4).
- `timeGetTime` and `QueryPerformanceCounter` are not imported by the exe; they are only in `rlmfc.dll`, so **all game time flows through `R_Timer` in rlmfc**. Replacing or scaling that one source is enough to control the game clock.
- Remaining frame-rate limit candidates: the driver's present interval (`D3DPRESENT_INTERVAL_*`, in `DRV_init` / `P_DisplayMode`) and anything inside `R_Timer::sample`.

### 8.2 Is 60 fps safe? Evidence so far (not a proof)

Searched all five code modules for hard-coded step-size floats (1/15, 1/20, 1/25, 1/30, 1/50, 1/60, 1/100, 1/120, as float and double) and checked who uses the interesting hits:

| Constant | Where | What it is |
|---|---|---|
| 1/30, `[0x7d0184]`, 1/15 (`0x7d0180..88`) | `FUN_00508930(dt)` | Returns `dt` times one of three factors, chosen by whether two specific keys (codes `0x36`, `0x9d`) are held. Looks like a **debug slow-motion** control, not a step size. |
| 1/60 (`0x7cce98`) | `FUN_00456d10` and 5 other sites | Used to split a time value into h/m/s for a **statistics printout**, i.e. a unit conversion. |
| 1/100, 1/50, 1/25, 1/20 | scattered `.rdata` hits in exe, e2mfc, rlmfc, sndmfc | Not yet traced; common small constants (0.01, 0.02, 0.04, 0.05) that may be unrelated to timing. |

- **No fixed-step constant (1/30 or 1/60) drives the simulation anywhere I looked**, and the top-level loop passes a smoothed, clamped, scaled `dt` down the mode tree (§8). That is consistent with variable timestep, so 60 fps looks safe, but I have **not** read the physics, AI or animation update code itself, so this is **unconfirmed**.
- The exe's functions are unnamed (only RTTI names exist), and each REA call re-imports the exe (~100 s), so reading virtuals one at a time is slow. **Next tool to build:** parse the RTTI complete-object-locators from the PE to map every vtable to its class name offline, then decompile the `update` slot of `MaxPayne_GameMode`, the character/AI classes and the physics classes directly.
- **Empirical check (cheap, once M2 runs):** force `R_Timer::sample` to return 1/60 s and 1/30 s for the same scripted input and compare character positions and ragdolls. Any fixed-step or frame-count-dependent code shows up as a divergence.
- A debug slow-motion path exists (keys `0x36` / `0x9d`), which is useful: scaling `dt` is something the game already tolerates over a wide range.

### 8.3 RTTI vtable mapper and the central game clock

**Tool:** `tools/vtables.py <module> <out.json>` parses MSVC RTTI (TypeDescriptor -> Complete Object Locator -> vtable) straight from the PE, no Ghidra needed. Results: exe 2,159 of 2,209 classes with vtables (13,284 slots), e2mfc 75, rlmfc 81, grphmfc 12, sndmfc 29, driver 48 (`census/vtables/*.json`). Vtable slot counts are heuristic (a run of pointers into `.text`), so adjacent vtables can merge or split. Multiple inheritance shows as several vtables per class (the COL `offset` field tells which base).

**Mode objects (exe):**
- Every mode class (`MaxPayne_GameMode`, `MaxPayne_HUDMode`, `MaxPayne_MenuMode`, ...) derives from `X_ModeBase`/`X_OverlaidModeBase`. The mode manager (`FUN_00601250`) calls **slot 14 (`+0x38`) as `update(dt)`** on each active mode. The base implementation of slot 14 is `0x60de10`; overrides: `MaxPayne_GameMode` -> `0x44c1b0`, `MaxPayne_HUDMode` -> `0x4aee20`, `MaxPayne_MenuMode` -> `0x42be90`. `X_HUDMode` leaves it pure virtual.
- `MaxPayne_GameMode::update` (`0x44c1b0`, ~1,400 lines of decompiled output, `census/decomp/exe_GameMode_update_0x44c1b0.c`) runs profiled sections named **Level, Camera, Level items, Projectiles, Decals, GlobalAI**. Each subsystem update is a virtual call **with no `dt` argument** and there is **no sub-step loop** in this function; the only loops walk lists of level objects once per frame.

**Why no `dt` argument:** time is published through a global clock.
- `X_TimeUpdate` (vtable `0x7d142c`, ctor `FUN_00582df0` -> `FUN_00582e60`) is built once per frame in `FUN_0040c020` with `(avgDt, totalTime, 1.0f)` and destroyed at the end of the frame (`FUN_00582e20`). Layout: `+4` dt, `+8` total time, `+0xc` scale, `+0x10` dt/scale (or dt if scale <= 0), `+0x14` total/scale, `+0x1c` valid flag. It publishes these to a global (`FUN_00583100`); the readers (`FUN_005830d0`, `FUN_005830f0`, ...) are what the simulation calls.
- Consequence for 60 fps: **one clock feeds everything**. Changing the frame rate means changing what `R_Timer::sample` returns; there is no second timing path in the game-mode update. The scale field (`+0xc`) is also the hook for bullet time.

**Not yet read (so the 60 fps verdict stays "likely safe, unconfirmed"):** the character update (`X_Character`, vtable `0x7d5950`, 31 slots), AI state machine (`MaxPayne_AIStateMachine`, `0x7cfcac`), projectile update (`X_Projectile`, `0x7d8134`), level-object base (`X_LevelRuntimeObjectBase`, `0x7d4e20`) and the collision code. These could still contain their own internal step or frame-count logic. There is no class named for physics, so movement and collision appear to be handled inside the character/level-object classes.

### 8.4 Update tree below the game mode (character, AI, projectile)

Traced with `FUN_00495930` (Ghidra) and, because Ghidra has no function there, `tools/disasm.py` (capstone, recursive descent, annotates float constants and import thunks). Listings: `census/decomp/exe_*.txt`.

```
MaxPayne_GameMode::update (0x44c1b0)
 └─ level update FUN_00495930(dt)          walks the level-object list (this+0xd7)
     ├─ obj->slot5 (+0x14)(dt)             "update"     \ both once per object, per frame
     └─ obj->slot6 (+0x18)(dt)             "post-update" /
         X_Character slot5 0x694280        -> children walker 0x6688c0(dt) on this+0x13d,
                                              then component->slot0(dt) for +0x37e and +0x37a
         X_Projectile slot5 0x708450       -> same walker 0x6688c0 (this adjusted by -0x1f)
         MaxPayne_AIStateMachine slot1 0x4fa180
                                           -> for each 0x5c-byte element: 0x4f8c70(dt)
                                                -> 0x4fd1c0(dt) x2, then member->slot1(dt)
```
- Every level passes `dt` straight down once. **No counter, no `while (accum >= step)` loop and no constant step size** appears on any traced path (character, projectile, AI state machine, children walker). The accessor-style leaves (`0x77f2f0` returns `this+0x1dd`) and forwarders are trivial.
- The leaves that actually integrate motion, animation and collision (`0x4fd1c0`, the `0x37a`/`0x37e` components, the Level items/Projectiles/Decals managers) were **not** read. They are the remaining place a hidden fixed step could live. Verdict stays **likely safe, confirm empirically** (force `dt` to 1/60 vs 1/30 in M2 and compare).

### 8.5 Function discovery gap (important for the lifter)
- `rea search --kind procedures` returns 15,701 addressable functions for the exe. Of **5,002 distinct vtable targets, 1,985 (40%) are not functions in Ghidra's list** (`census/ghidra/exe_vtable_targets_missing.json`), e.g. `X_Character::update` (`0x694280`), `X_Projectile::update` (`0x708450`). REA's decompile fails on them ("File offset ... has no loaded source mapping") because it falls back to treating the address as a file offset.
- Consequence: **function discovery for the static lift must be seeded from the RTTI vtables** (`tools/vtables.py`), plus the DLL export tables, not left to Ghidra auto-analysis. Same for any indirect call target we can recover. Do this seeding before M5.
- Practical consequence now: use `tools/disasm.py` for vtable-only functions until we can feed seeds to Ghidra.

### 8.6 Leaf updates: projectile mover, managers, AI sub-object

Read with `tools/disasm.py` (listings in `census/decomp/exe_0x*.txt`).

- **Clock getters are plain field reads** of an `X_TimeUpdate`: `0x5e53d0` -> `[this+4]` (dt, s), `0x5830d0` -> `[this+8]` (total time), `0x5830e0` -> `[this+0xc]` (scale), `0x5830f0` -> `[this+0x14]` (scaled total). The clock object is passed down as the `dt` argument of every update virtual.
- **Projectile manager** (`X_ProjectileImplementation` slot 1, `0x65a950`): loops over its projectile arrays once per frame and calls the projectile mover `0x707070(clock)` for each live one (or a removal path). One call per projectile per frame.
- **Projectile mover** (`0x707070`, 419 instructions, 103 x87 ops) has the only loop-like construct found so far:
  - `N = clock.dt`. `while (N > 1.0 && !0x7078a0(this))` it publishes a local `X_TimeUpdate` with **dt = 1.0** and calls the integrator `0x707670`, then `N -= 1.0`. After the loop, if `N > 0`, it does **one** more step with **dt = N**.
  - So the integrator is called once with the real `dt` per frame. The loop is a guard that cuts a huge `dt` (> 1 s) into 1-second pieces, which cannot happen because the main loop clamps `dt` to 0.1 s (§8). **It does not depend on frame count or frame rate.**
- **Level-item manager** (`X_LevelItemImplementation` slot 5, `0x66f5c0`): no `dt` at all. Walks a sorted tree of items once per frame and updates the ordering; unrelated to time.
- **AI sub-object** (`0x4fd1c0`, 233 instructions): no x87 at all, string/token handling and calls into script code. Not time-driven.
- Still unread: the integrator `0x707670`, the character components at `+0x37a`/`+0x37e`, camera, and animation playback. These consume `dt` but, from the call graph above, never receive anything except the single per-frame clock.

**Verdict on 60 fps:** every traced update path receives one smoothed, clamped `dt` per frame and steps once. No fixed 1/30 or 1/60 step, frame counter or accumulator was found. **Likely safe**; the remaining proof is the empirical test in M2 (force `dt` to 1/60 and 1/30 on identical input and diff the results).

## 9. Open items and next steps
